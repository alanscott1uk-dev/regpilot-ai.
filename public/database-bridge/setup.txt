Native SQL collection

PostgreSQL, MySQL, Microsoft SQL Server and ClickHouse can run directly on an authorised Python host. Download the individual native SQL plan and the collection ZIP from /database-integrations. Unpack the ZIP. In a Python virtual environment, install the package versions in the plan's install field with python -m pip install. Keep native_sql.py beside collect.py and watch.py. The runner verifies the native module digest and the selected driver version on each invocation.

Use a private local config with host, port, database, username and password. PostgreSQL and SQL Server accept a schemas list, defaulting to public and dbo respectively. TLS verifies the server by default. Set caFile to the path of your trusted CA bundle for a private certificate authority. An explicitly selected private-network transport is available on a trusted local network. Use a read-only account restricted to approved tables or views. Only the selected control and optional resource identifier columns are read. A scan exceeding 20,000 rows fails and requires a narrower view. Checks, discovery, rules, submission and scheduling use the same commands below. Native SQL runs on the host network.

Manual database and API collection

1. Download a JSON plan from /database-integrations. Review the connector licence, version and configuration instructions at the documentation URL in the plan. Install the approved vendor image on an authorised Linux host with Python 3.10+ and Docker. Verify the image digest through your approved software supply process. The runner requires the local image tag, the independently approved repository digest and the digest in the checked plan to match.

2. Create a local source config from the vendor documentation using a read-only source credential. Limit the account to the data you need. Keep the config owner-readable only. Use a dedicated Docker network with access to the specific upstream service. Credentials are supplied only to the installed vendor connector.

3. Download collect.py. Use --check-access to test the source credential. List full-refresh streams, namespaces and field names. Replace DIGEST with sha256: followed by the approved 64-character image digest.

python3 collect.py --plan plan.json --config config.json --digest DIGEST --network source-network --list-streams

4. Choose a stream, a top-level control field and a JSON scalar to compare. Supply the exact namespace reported by discovery. Omit --namespace when the source reports null. This example checks whether all decision values are the string approved.

python3 collect.py --plan plan.json --config config.json --digest DIGEST --network source-network --stream release_gate --namespace public --field decision --expected '"approved"' --control CONTROL_UUID --output observation.json

The rule compares JSON type and value. A different value produces FAIL. Missing values or an empty stream without any failures produce UNKNOWN. An incomplete or rejected read exits without publishing a receipt. A successful envelope contains aggregate counts, the image digest and a fingerprint of the stream, namespace, field and expected value. Keep the control specification and approvals for the rule in your workspace. Each command has a five-minute limit and a 128 MiB output limit. Scope large databases to an approved reporting view or a smaller stream.

5. Create an observations:write credential for the target control in the private workspace. Submit the saved envelope with deliver.py. It prompts for the credential or reads REGPILOT_OBSERVATION_TOKEN.

python3 deliver.py observation.json --workspace https://YOUR-REGPILOT-WORKSPACE

Retry a delivery using the same envelope. A later manual read requires a new output path. Source observations enter the existing review queue. A workspace reviewer can open a follow-up for failed checks.

The catalogue API is GET /api/database-integrations with optional q, kind and page parameters. Each available plan link pins the catalogue version. When a version changes, download and review the new plan and digest before running it.

Download all currently checked plans from /api/database-integrations/manifest. Pass the manifest as --plan and choose one definition UUID with --source. Each entry includes the checked Linux image digest, version, configuration field names and required fields.

For nested fields, replace --field with a JSON Pointer such as --pointer /instrument/readings/0/value. Escape a slash inside a key as ~1 and a tilde as ~0. To apply an approved numeric range, replace --expected with --minimum and --maximum. Both limits are inclusive. For example, --pointer /instrument/readings/0/value --minimum 2 --maximum 8 checks the selected value in each record. Select the stream and units covered by your control. A numeric excursion produces FAIL. Missing or nonnumeric values produce UNKNOWN when there are no excursions. Receipts contain aggregate counts.

Resource findings and rechecks

To identify affected records, add --resource-pointer /id and --instance warehouse-east to the collection command. Choose a stable instance name unique to this account or site and an identifier you are authorised to share with your RegPilot workspace. Only the selected IDs appear in the resource checks. The remaining row values stay on the source host.

Up to 16 resource results accompany each receipt. Add --track 42 for an integer ID or --track '"LOT-12"' for a string ID to follow a particular record even if the next scan omits it. Tracked IDs appear first, then failing, unknown and passing resources. The coverage check shows omitted counts, duplicate IDs and unidentified rows. Aggregates cover every row scanned.

Repeat the same rule and instance after correcting the source and deliver the new receipt. In Company integrations, open the observation and choose Inspect affected resources to see earlier failures, later passing readings and missing records. Download findings and receipt history for the reviewer. A changed rule, control specification, source instance or resource selector starts a separate history.

To build the rule in RegPilot, search the source catalogue, expand Create a custom monitoring test, choose the source and control, then download source-test.json. Use the individual plan for that source version. You can add --track when the saved definition includes a resource ID field.

python3 collect.py --plan plan.json --config config.json --digest DIGEST --network source-network --test-definition source-test.json --output observation.json

For a bulk manifest add --source DEFINITION_UUID. The runner checks the test's source and version against the plan before collection.

Set an optional remediation target in the test builder or use --remediation-days 7 with a resource selector. At each reading, overdue findings appear first. The first observed failure in the available history sets the deadline. An explicit later pass ends that failure period. Missing readings keep the last known failure visible.

Scheduled source checks

Put watch.py beside collect.py on the authorised Linux collection host. Use one private spool directory for each source instance and rule. Keep the config at the same path when rotating its credential. Invoke the command from your host timer at least once per chosen interval. Overlapping invocations and repeats in the same interval skip the duplicate read.

python3 watch.py --plan plan.json --config config.json --digest DIGEST --network source-network --test-definition source-test.json --directory /var/lib/regpilot/warehouse-check --interval-seconds 3600

A failed interval identifies the step that stopped and the corresponding recovery action. After access is restored, the successful receipt points back to the failed slot.

Each attempted interval produces a status file and an availability observation. A successful collection also produces the ordinary source observation. Download the complete runner ZIP from /api/tools/database-bridge and unpack it on the collection host. Set REGPILOT_OBSERVATION_TOKEN in the timer’s private environment and add --workspace https://YOUR-REGPILOT-WORKSPACE to the watch command. Each invocation forwards up to twelve completed slots, even when the next source check is not yet due. Delivery resumes from the last confirmed envelope after an outage. Each envelope keeps its original idempotency key. Expired observations are retained on disk and marked EXPIRED_WITHOUT_CONFIRMATION. A new source read gets its own timestamp. A failure creates no source observation. The next invocation counts intervals skipped while the host was stopped. Keep the spool until delivery and retention requirements have been met.
