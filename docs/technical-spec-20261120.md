# RegPilot competitive technical specification — 20 November 2026

## Delivery order

The current user instruction is to add advanced capabilities and their supporting infrastructure first, bring the application to a defined technical specification, then complete workflow and visual refinement. This supersedes a workflow-only development priority. Every new capability still needs meaningful correctness, tenant-isolation and persistence verification as it is built; those checks are part of implementing the capability.

This is the active technical baseline. Historical feature notes must not be mistaken for current gaps or counted again as new development. A screen, connector name or mock response is insufficient evidence that a capability is implemented. The development branch and [PR #10](https://github.com/alanscott1uk-dev/regpilot-ai./pull/10) record the exact source revision, executed checks and remaining failures. A subsequent review deployment is a separate action; the 19 November preview does not contain this batch.

### Implemented infrastructure

- Additive schema migration with composite company/questionnaire and company/answer foreign keys, unique operation/input constraints, state checks and indexes. The new table is closed to Supabase Data API roles in the same migration. The restricted staging application role receives only its existing private-runtime pattern when present.
- Short serializable company transactions and membership locks protect state changes. Draft history and reusable answer-library checks read shared evidence and participant state in bounded bulk projections rather than querying them again per record. Storage retrieval, extraction and model calls execute outside transaction locks; final state is recaptured before commit.
- Existing organisation/platform paid reservations and per-user/per-company AI quotas apply. Questionnaire preparations additionally have a bounded daily organisation allowance. Failed or interrupted paid attempts remain counted because a provider may have accepted them.
- Production package traces include the PDF and DOCX workers and parser dependencies for both prepare and save routes. Isolated runtime tests exercise the packaged workers rather than relying on development imports.
- Database, HTTP, domain and file-parser tests are registered in the existing CI. The new additive migration is included in the baseline-to-current schema drift check and the private-table checks.
- The interface exposes technical capabilities through the existing company context, with explicit unknown-outcome recovery. It is not a second disconnected application or a simulation of provider behaviour.

## Advanced capability expansion — 20 November

Three further capabilities now have dedicated data models, server APIs and workspace screens. The final revision and execution evidence belong in PR #10; the descriptions here concern the implemented source and its explicit boundaries.

### Maintained company knowledge

`/team/knowledge` indexes independently approved private PDF and DOCX originals. It verifies stored bytes, extracts bounded page/block chunks and persists source versions, participant permissions, exact UTF-16 quotation offsets, content hashes, processing status and expiry. Unchanged current sources reuse their index; failed attempts require explicit retry. Changes to evidence, permissions or applicable product scope withhold dependent search results. Removing an index deletes its extracted text and vectors while retaining the source and operation history.

Content search ranks matching terms without a model call. Semantic search uses the installed AI SDK embedding adapter and actual cosine similarity over persisted vectors. The provider/model is explicitly configured by `REGPILOT_KNOWLEDGE_EMBEDDING_MODEL`; `REGPILOT_KNOWLEDGE_SEMANTIC_ENABLED` defaults off and retains all existing AI, privacy and paid-service gates. No live provider has been activated or evaluated by this build. Search scores are relevance measures, not confidence or evidence sufficiency.

The bounded index supports 40 documents, 40 chunks and 42,000 extracted characters per document, 1,600 company chunks and vectors up to 1,536 dimensions. Extraction rejects incomplete documents rather than silently indexing a partial source. These are supported implementation bounds, not measured production capacity. The implementation uses bounded JSON vectors and in-process ranking, not a distributed vector database. Normalised embedding directions are stored as bounded integer components, and result scores as fixed-decimal strings, to preserve integrity hashes through PostgreSQL JSON round trips; the API returns numeric relevance scores. Historical operation records do not permanently exhaust a lifetime search allowance. Exact request receipts also recover a cached index reuse after a lost acknowledgement.

Each semantic indexing operation reserves one daily AI request and a conservative paid allowance of at most one unit per bounded chunk; provider splitting remains serial and has no automatic retries. Query embeddings are reused for the same company/query/model when valid. Provider-reported usage and actual input counts are recorded. The questionnaire preparation screen can search company knowledge, inspect citations and select up to three sources; preparation then re-verifies the original private documents before saving any answer.

### Multiple products in one assurance response

`/team/products` manages distinct company products with versioned code, name, description and active/archive state. Reviewed evidence can be explicitly global or assigned to selected products. Existing unscoped files and legacy answers retain their original meaning and are not silently promoted to global use. Evidence scope changes increment its review version; relevant product metadata changes invalidate affected answers, draft context and disclosure reliance.

Questionnaire intake can expand each original source question for up to ten selected products within the existing 100-response limit. Each response has its own identity, owner confirmation and product-bound answer. Exact source references, sheets, rows and cells remain attached. Only an answer for the matching product, or an explicitly approved global answer supported by global evidence, can be suggested, confirmed or disclosed. An unrelated product change does not invalidate a different product's unchanged preparation. Combined clean CSV/XLSX responses and provenance include product identity; faithful recreation of the customer's original workbook remains outside this implementation.

### Dedicated deviations and CAPA

`/team/quality` adds deviation/CAPA classification, occurrence and impact, containment, investigation findings, root cause, owned corrective/preventive actions, measurable effectiveness criteria and a planned observation date. Actions link actual ordinary tasks or create owned work. A completed flag alone cannot satisfy an action: effectiveness preparation checks its saved completion receipt, current source/assessment/control basis, current reviewed evidence and responsible participants, then verifies private bytes again.

An independent eligible administrator decides the observed effectiveness. Passing cannot close a case before the planned observation date; a failed observation opens a new investigation cycle. Recurrence and reassessment preserve prior actions, observations and decisions and require new investigation and action context. Due/overdue queues, exact case links, attributed chronology exports and immutable operation receipts support actual use and recovery. Recorded closure and current supported closure remain distinct if later evidence or permissions change.

The implementation supports 200 simultaneously open cases, ten actions per cycle, forty assessment/cycle records per case and thirty unique supporting files per reviewed cycle. These bounds are explicit. This module is internal quality recordkeeping; it does not establish GxP validation, a compliant electronic-signature system, GMP certification or complete pharmaceutical QMS parity. Dedicated training curricula, revision-triggered retraining, effectiveness quizzes and document effectivity controls remain work.

### Shared infrastructure for the expansion

Ten private tables are added through three additive migrations: products/evidence applicability; knowledge indexes/chunks/searches; and quality cases/actions/effectiveness/operation receipts. Composite foreign keys bind linked records to one company. Migrations include table checks, indexes, private API-role revocation and the existing restricted runtime-role pattern. The baseline migration replay, schema drift gate and private-table checks include every new table. PDF/DOCX production runtime traces include all knowledge routes.

Existing company/authentication boundaries, human review, private storage verification and paid-service switches remain the authorities for these additions. Provider-controlled contract tests establish adapter behaviour, and actual disposable-service browser acceptance establishes the application path. Neither substitutes for live model evaluation, hosted operational configuration, sustained production load or independent sector validation.
